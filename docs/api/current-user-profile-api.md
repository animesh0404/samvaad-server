# Current user and profile API

This is the current implemented HTTP API, not the planned authentication or
messaging protocol. Authentication and authorization are not implemented yet.

## `POST /api/users`

Creates a user and its empty profile. The current request/response DTO includes
`userId`, `username`, and `email`; `userId` is generated by the server.

- `username` is required and validates as `[a-zA-Z0-9_]+`, length 3–32.
- `email` is currently optional.

This endpoint is not yet the designed password-based registration flow.

## `GET /api/users/{userId}`

Returns the current user DTO. A missing user returns HTTP 404.

## `GET /api/users/{userId}/profile`

Returns the profile DTO with `userId`, `displayName`, `bio`, `avatarUrl`,
`firstName`, `middleName`, `lastName`, and `statusMessage`. A missing profile
returns HTTP 404.

## `PATCH /api/users/{userId}/profile`

Accepts `UserProfileUpdateDto` with these optional fields:

`displayName`, `bio`, `avatarUrl`, `firstName`, `middleName`, `lastName`, and
`statusMessage`.

The accepted contract is:

| Request field state | Required result |
| --- | --- |
| Omitted | Leave existing value unchanged |
| Present with non-null value | Replace existing value |
| Present with `null` | Clear existing value |

### Known gap

The current implementation only updates non-null DTO values. Java binding
currently represents both an omitted property and an explicit JSON `null` as
`null`, so explicit clearing is not yet implemented. This document records the
accepted API contract; it does not claim the gap is solved. See ADR 0006.
